[1] 시작 — 조사만 (시작문 아래에 붙인다)
시험 종료 시각은 <HH:MM>이고 지금 시각은 <HH:MM>이야(과제 지문 속 시각과는 별개야). 추가 파일 반입은 <내가 확인했어 / 아직 확인 못 했어>. 패키지 설치는 <허용 / 금지 / 모름>이야.
조사 결과에는 다음을 넣어줘. 아직 구현하지 마. 답은 내가 정할 것부터 써줘: 닫힌 질문과 갈래별 비교 표 → 모델 시트 → 한 가지로 읽은 것 → 나머지(각각 서너 줄). 같은 내용을 두 번 쓰지 마.
1) 이 과제가 최적화인지, 최적화라면 일정·배정 / 수량 배분 / 선택·덮기 / 공정 조건 탐색 중 무엇인지와 근거.
2) 지문의 모든 문장에 태그(집합·데이터·결정·필수·목적·정의·출력·미확정)를 붙이되, 표에는 목적·정의·출력·미확정 문장만 보이고 나머지는 개수만. 필수 문장은 모델 시트의 원문 인용으로 충분해.
3) 한 장짜리 모델 시트: 집합과 색인, 데이터와 단위, 결정변수, 필수 제약(ID·원문 인용·식·검증 방법), 목적과 우선순위, 정의, 출력 형식, 완료 기준(제안). 최적화가 아니면 요구사항 표(요구 ID, 원문 인용, 입력 → 처리 → 출력, 판정 규칙과 경계값, 검증 방법)로 바꿔 내줘.
4) 지문만으로 정해지지 않는 것. 결과를 바꾸는 닫힌 질문은 중요한 순서로 최대 5개, 질문마다 네 잠정 선택을 붙여서. 지문에 없어 한 가지로 읽은 것은 따로.
5) 남은 시간을 조사·합의 / 첫 동작 / 확장 / 검증 / 제출 확인에 어떻게 나눌지 한 줄 제안.
6) 쓸 수 있는 솔버와 패키지를 import로만 확인한 결과와 버전. 설치는 하지 마.
지문과 데이터에 없는 입력값은 만들지 마. 손으로 계산해 본 값은 미검증이라고 표시해줘. 내 해석을 줄 때까지 기다려.

[2] 내 해석과 대조
내 해석은 이래: <정하는 것 / 반드시 지킬 것 / 더 좋게 할 것 / 헷갈리는 것>.
네 모델 시트와 제약 ID별로 비교해서 다른 곳만 표로 보여줘. 어느 쪽이 지문 원문에 맞는지 원문을 인용해서 말하고, 원문으로 가릴 수 없는 것은 질문 목록으로 넘겨줘.

[3] 담당자에게 물을 질문 만들기 ([1]의 4)가 이미 "A인가 B인가" 꼴이면 이 문구 없이 바로 물어도 된다)
미확정 항목 중 답에 따라 모델이나 결과가 달라지는 것만 골라 질문을 만들어줘.
질문마다 "A인가 B인가" 형태로 쓰고, A일 때와 B일 때 무엇이 달라지는지 한 줄씩 붙여줘.
다음이 지문으로 정해지지 않았다면 후보에 넣어줘: 대기 한도(Q-Time)의 기준 사건과 경계값 포함 여부, 납기가 필수인지 지연 벌점인지, 우선순위(긴급 로트 등)가 필수인지, 목적이 여럿일 때의 순서, 진행 중인 작업과 이미 흐른 시간의 처리, 정비에 걸치는 작업을 멈췄다 이어 할 수 있는지, 제출 형식에서 같은 로트의 재방문을 구분하는 방법.
중요한 순서로 최대 <5>개만 질문으로 만들고, 나머지는 잠정 선택과 함께 한 줄씩 적어줘.

[4] 담당자 답 반영
담당자 답: <답 원문>.
답을 필수 조건 / 기존 요구의 구체화 / 선택적 개선 / 공식 지시와의 충돌로 구분하고, 모델 시트의 어느 제약 ID가 어떻게 바뀌는지 바뀐 행만 보여줘.
구현 승인 전이면 거기서 멈추고, 이미 구현 중이면 영향받는 코드와 검사만 고쳐 다시 검증해줘.

[5] 구현 진행
구현 진행. 범위는 합의한 모델 시트 그대로야. 답을 못 받은 질문은 시트의 잠정 선택으로 두고, 답이 오면 한 곳만 고치면 되게 해줘.
시작 전에 합의한 모델 시트와 담당자 답을 작업 기록에 옮겨 적어줘.
순서는 이렇게 해줘.
1) 원본 입력과 최종 출력만으로 제약 ID마다 다시 계산하는 독립 검증기를 먼저 만든다(솔버 라이브러리를 쓰지 않는다).
2) 가장 작은 실제 입력으로 입력 → 모델 → 검증 → 출력을 끝까지 잇는다. 과제가 화면을 요구하면 필수 화면에 그 결과가 뜨는 데까지가 이 단계다(꾸미기는 나중).
3) 그다음에 전체 입력으로 넓힌다.
(일정 문제일 때만) 작업 단위는 (로트, 방문 회차)로 두고, 적합한 (방문, 장비) 쌍에만 변수를 만들어줘.
시간은 배율을 곱해 정확히 정수로 만들고, 필수 제약은 벌점으로 완화하지 마. 솔버를 부를 때는 시간 한도를 넣어줘.
솔버가 없으면 PROCESS_OPTIMIZATION 1절대로 하되, 설치가 필요하면 먼저 물어봐.

[5-1] 답을 기다리는 동안
구현 진행. 단 질문과 무관한 부분만 해줘(입력 읽기, 독립 검증기, 화면 뼈대). 질문에 걸린 제약은 아직 넣지 마.

[6] 검증기 점검
검증기가 실제로 잡아내는지 보여줘. 올바른 결과 하나에서, 모델 시트의 필수 제약 ID마다 그 제약만 어기도록 깨뜨린 결과를 하나씩 만들어 넣어줘.
(일정 문제의 예: 방문 하나 누락, 같은 로트의 두 방문 뒤바꿈, 부적합 장비 배정, 같은 장비에서 겹침, 대기 한도 초과, 진행 중 작업 변경, 정비 시간 침범, 현재 시각보다 앞선 시작.)
깨뜨린 내용 / 검증기 출력 / 잡았는지 여부를 표로 보여줘. 못 잡은 것이 있으면 검증기를 고치고 다시 실행해줘.

[7] 결과 보고
현재 결과를 이렇게 보고해줘.
- 솔버 종료 상태, 목적값, 하한(최대화면 상한), 격차, 시간 한도. "최적"이라는 말은 최적성이 확인됐을 때만.
- 제약 ID별 검증 결과(위반 건수)와 검증에 쓴 입력·코드 버전.
- 지표 표: 정의, 단위, 분모.
- (과제가 비교를 요구하거나 시간이 남을 때만) 단순 규칙을 같은 입력·같은 검증기로 평가한 비교. 규칙이 필수 제약을 어기면 그렇게 적어줘.
- 가정(잠정 선택 포함), 미확정, 한계.
- 화면이 있으면 내가 브라우저에서 확인할 주소, 누를 순서, 기대 결과. 내 관측을 받기 전에는 화면 검증을 미실행으로 적어줘.
실행하지 않은 검사는 미실행이라고 적어줘.

[8] 해 없음이 나왔을 때
종료 상태가 불가능 증명(INFEASIBLE)인지 시간 안에 못 찾은 것(UNKNOWN)인지 먼저 말해줘. 시간 안에 못 찾은 것이면 [10]으로 가.
불가능 증명이면 조건을 완화해서 풀지 말고 원인부터 찾아줘.
제약 묶음(ID)을 하나씩 빼고 풀어서 어느 묶음을 빼면 풀리는지 표로 보여줘. 그 묶음의 식을 지문 원문과 나란히 놓고 부호, 경계값 포함 여부, 분모, 단위, 기준 사건, 초기 상태, 시간 범위를 대조해줘.
독해 오류가 아니라 입력 자체가 모순이면 어느 로트·어느 조건이 부딪히는지 구체적으로 적어줘.

[9] 해가 너무 쉬울 때
결과가 너무 좋아 보여(<지연 0 / 자원이 크게 남음 / 완료가 너무 빠름>). 빠뜨린 문장이 있는지 확인해줘.
방문(작업 단위)의 수가 로트별 경로 단계 수의 합과 같은지, 지문의 모든 필수 문장에 제약 ID가 붙어 있는지, 단계를 잇는 식(배정과 사용, 선택과 덮기)이 빠지지 않았는지, 현재 시각보다 앞에서 시작하는 새 작업이 없는지 세어서 보여줘.

[10] 시간 안에 안 풀릴 때
전체 입력이 <N>초 안에 최적성 확인이 안 돼. 다음을 순서대로 해줘.
1) 지금까지의 가장 좋은 유효해와 하한, 격차를 보고한다. 유효해가 검증을 통과했으면 여기서 멈춰도 된다.
2) 유효해가 아직 없으면 단순 규칙으로 유효한 일정을 먼저 만든다.
3) (내가 시간이 남았다고 할 때만) 나눠 풀 수 있는지 본다. 부분들이 공유 자원·대기 한도·예산으로 이어져 있으면 합친 결과를 전체 검증기로 다시 검사하고 "나눈 범위 안의 최선"이라고 적는다.
필수 제약을 빼거나 대상을 줄이지 마. 시간 제한을 불가능의 증명처럼 쓰지 마.

[11] 설명 연습
지금 구조를 다섯 줄로 설명해줘: 무엇을 정하는가 / 반드시 지킨 조건 / 무엇을 좋게 했는가 / 어떻게 검증했는가 / 남은 위험.
그다음 내가 직접 설명할 수 있는지 질문을 하나만 내고 내 답을 기다려줘. 답하기 전에 정답을 말하지 마.

[12] 제출 전 점검
제출 전에 확인해줘: 제출 형식과 파일 이름, 다시 실행하는 명령, 최종 입력으로 다시 돌린 검증 결과, 화면이 있으면 내가 확인한 관측 기록, 사용한 지침의 제출 여부(QUICKSTART의 제출 확인), 비밀정보 포함 여부, 미검증 항목과 한계.
구현 완료, 검증 통과, 실제 제출 완료를 구분해서 적어줘.

[13] 세션을 다시 열었을 때
playbook/AGENTS.md, PLAYBOOK.md와 앞서 쓴 조건부 문서, 작업 기록을 읽고 이어서 해줘. 구현 진행은 이미 승인했고 범위는 작업 기록의 모델 시트야. 조사와 합의를 다시 하지 말고, 마지막으로 통과한 검사부터 확인해줘.
