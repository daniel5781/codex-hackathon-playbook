공정 운영 최적화 과제용 요청 문구 모음
- 플레이북의 시작문으로 세션을 연 뒤, 과제가 공정 운영 최적화로 보일 때 단계에 맞는 것만 골라 쓴다. <...> 안은 그때 채운다.
- 공식 과제 지시와 운영 규정이 항상 우선한다. 조사·합의와 "구현 진행" 승인 절차는 PLAYBOOK.md를 따른다. 허용되지 않은 설치·외부 전송·우회는 요청하지 않는다.

[1] 시작 — 조사만
공식 과제 README와 제공 데이터, 기존 코드를 원본 변경 없이 읽어줘. 플레이북 경로의 PROCESS_OPTIMIZATION.md 도 읽어줘.
제한 시간은 <N>분이고 지금은 <HH:MM>이야.
아직 구현하지 말고 다음만 해줘.
1) 이 과제가 최적화인지, 최적화라면 일정·배정 / 수량 배분 / 선택·덮기 / 공정 조건 탐색 중 무엇인지와 근거.
2) 지문의 모든 문장에 태그(집합·데이터·결정·필수·목적·정의·출력·미확정)를 붙인 표.
3) 한 장짜리 모델 시트: 집합과 색인, 데이터와 단위, 결정변수, 필수 제약(ID·원문 인용·식·검증 방법), 목적과 우선순위, 정의, 출력 형식.
4) 지문만으로 정해지지 않는 것의 목록.
지문과 데이터에 없는 수치는 만들지 마. 내 해석을 줄 때까지 기다려.

[2] 내 해석과 대조
내 해석은 이래: <정하는 것 / 반드시 지킬 것 / 더 좋게 할 것 / 헷갈리는 것>.
네 모델 시트와 제약 ID별로 비교해서 다른 곳만 표로 보여줘. 어느 쪽이 지문 원문에 맞는지 원문을 인용해서 말하고, 원문으로 가릴 수 없는 것은 질문 목록으로 넘겨줘.

[3] 담당자에게 물을 질문 만들기
미확정 항목 중 답에 따라 모델이나 결과가 달라지는 것만 골라 질문을 만들어줘.
질문마다 "A인가 B인가" 형태로 쓰고, A일 때와 B일 때 무엇이 달라지는지 한 줄씩 붙여줘.
특히 다음을 빠뜨리지 마: 대기 한도(Q-Time)의 기준 사건과 경계값 포함 여부, 납기가 필수인지 지연 벌점인지, 우선순위(긴급 로트 등)가 필수인지, 목적이 여럿일 때의 순서, 진행 중인 작업과 이미 흐른 시간의 처리.
중요한 순서로 최대 <5>개만.

[4] 담당자 답 반영
담당자 답: <답 원문>.
답을 필수 조건 / 기존 요구의 구체화 / 선택적 개선 / 공식 지시와의 충돌로 구분하고, 모델 시트의 어느 제약 ID가 어떻게 바뀌는지 보여줘. 바뀐 시트를 다시 내줘. 아직 구현하지 마.

[5] 구현 진행
구현 진행. 범위는 합의한 모델 시트 그대로야.
순서는 이렇게 해줘.
1) 원본 입력과 최종 출력만으로 제약 ID마다 다시 계산하는 독립 검증기를 먼저 만든다(솔버 라이브러리를 쓰지 않는다).
2) 가장 작은 실제 입력으로 입력 → 모델 → 검증 → 출력을 끝까지 잇는다.
3) 그다음에 전체 입력으로 넓힌다.
작업 단위는 (로트, 방문 회차)로 두고, 적합한 (방문, 장비) 쌍에만 변수를 만들어줘. 시간은 배율을 곱해 정확히 정수로 만들고, 필수 제약은 벌점으로 완화하지 마.
솔버는 설치 여부를 먼저 확인하고, 없으면 허용된 범위에서 어떻게 할지 물어봐.

[6] 검증기 점검
검증기가 실제로 잡아내는지 보여줘. 올바른 일정 하나에서 일부러 깨뜨린 일정을 만들어 각각 넣어줘: 방문 하나 누락, 같은 로트의 두 방문 뒤바꿈, 부적합 장비 배정, 같은 장비에서 겹침, 대기 한도 초과, 진행 중 작업 변경, 정비 시간 침범.
깨뜨린 내용 / 검증기 출력 / 잡았는지 여부를 표로 보여줘. 못 잡은 것이 있으면 검증기를 고치고 다시 실행해줘.

[7] 결과 보고
현재 결과를 이렇게 보고해줘.
- 솔버 종료 상태, 목적값, 하한, 격차, 시간 한도. "최적"이라는 말은 최적성이 확인됐을 때만.
- 제약 ID별 검증 결과(위반 건수)와 검증에 쓴 입력·코드 버전.
- 지표 표: 정의, 단위, 분모.
- 단순 규칙(먼저 온 순서 등)을 같은 입력·같은 검증기로 평가한 비교. 규칙이 필수 제약을 어기면 그렇게 적어줘.
- 가정, 미확정, 한계.
실행하지 않은 검사는 미실행이라고 적어줘.

[8] 해 없음이 나왔을 때
모델이 불가능으로 나왔어. 조건을 완화해서 풀지 말고 원인부터 찾아줘.
제약 묶음(ID)을 하나씩 빼고 풀어서 어느 묶음을 빼면 풀리는지 표로 보여줘. 그 묶음의 식을 지문 원문과 나란히 놓고 부호, 경계값 포함 여부, 분모, 단위, 기준 사건, 초기 상태를 대조해줘.
독해 오류가 아니라 입력 자체가 모순이면 어느 로트·어느 조건이 부딪히는지 구체적으로 적어줘.

[9] 해가 너무 쉬울 때
결과가 너무 좋아 보여(<지연 0 / 자원이 크게 남음 / 완료가 너무 빠름>). 빠뜨린 문장이 있는지 확인해줘.
구간 변수의 수가 경로표의 행 수와 같은지, 지문의 모든 필수 문장에 제약 ID가 붙어 있는지, 단계를 잇는 식(배정과 사용, 선택과 덮기)이 빠지지 않았는지 세어서 보여줘.

[10] 시간 안에 안 풀릴 때
전체 입력이 <N>초 안에 최적성 확인이 안 돼. 다음을 순서대로 해줘.
1) 지금까지의 가장 좋은 유효해와 하한, 격차를 보고한다.
2) 같은 입력에서 단순 규칙으로 만든 유효한 일정을 기준으로 둔다.
3) 나눠 풀 수 있는지 본다. 부분들이 공유 자원·대기 한도·예산으로 이어져 있으면 합친 결과를 전체 검증기로 다시 검사하고 "나눈 범위 안의 최선"이라고 적는다.
필수 제약을 빼거나 대상을 줄이지 마. 시간 제한을 불가능의 증명처럼 쓰지 마.

[11] 설명 연습
지금 구조를 다섯 줄로 설명해줘: 무엇을 정하는가 / 반드시 지킨 조건 / 무엇을 좋게 했는가 / 어떻게 검증했는가 / 남은 위험.
그다음 내가 직접 설명할 수 있는지 질문을 하나만 내고 내 답을 기다려줘. 답하기 전에 정답을 말하지 마.

[12] 제출 전 점검
제출 전에 확인해줘: 제출 형식과 파일 이름, 다시 실행하는 명령, 최종 입력으로 다시 돌린 검증 결과, 비밀정보 포함 여부, 미검증 항목과 한계.
구현 완료, 검증 통과, 실제 제출 완료를 구분해서 적어줘.
