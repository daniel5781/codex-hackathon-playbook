요청 문구 모음 (최적화 과제 중심, 다른 과제에도 쓴다)
- 기본 흐름은 넷이다: [1] 시작 → [5] 구현 진행 → [7] 결과와 검증 보고 → [12] 제출 전 점검. [1]은 QUICKSTART의 메인 시작문 바로 아래에 붙여 한 번에 보낸다.
- 나머지는 필요할 때만 쓴다: [2] 내 해석과 대조, [4] 담당자 답 반영, [6-1] 검증만 다시, [8] 해 없음, [9] 너무 쉬운 해, [10] 계산 시간 관리, [13] 세션 재개.
- <...> 안은 그때 채운다. 최적화가 아닌 과제에서는 [5] 대신 PLAYBOOK "작업 흐름" 표의 짧은 요청을, [7] 대신 [6-1]을 쓴다. 번호는 예전 그대로이고 빠진 번호는 없앤 문구다.
- 공식 과제 지시와 운영 규정이 항상 우선한다. 조사·합의와 "구현 진행" 승인 절차는 PLAYBOOK.md를 따른다. 허용되지 않은 설치·외부 전송·우회는 요청하지 않는다.

[1] 시작 — 조사만 (시작문 아래에 붙인다)
시험 종료 시각은 <HH:MM>이고 지금 시각은 <HH:MM>이야(과제 지문 속 시각과는 별개야). 추가 파일 반입은 <내가 확인했어 / 아직 확인 못 했어>. 패키지 설치는 <허용 / 금지 / 모름>이야.
조사 결과에는 다음을 넣어줘. 아직 구현하지 마. 답은 내가 정할 것부터 써줘: 닫힌 질문과 갈래별 비교 표 → 모델 시트(1번과 2번도 여기에) → 한 가지로 읽은 것 → 나머지(각각 서너 줄). 같은 내용을 두 번 쓰지 마.
1) 이 과제가 최적화인지, 최적화라면 일정·배정 / 수량 배분 / 선택·덮기 / 공정 조건 탐색 중 무엇인지와 근거.
2) 지문의 모든 문장(제목, 표의 행, 괄호 주석 포함)이 모델 시트의 어느 칸에 들어갔는지 확인하고, 어디에도 들어가지 않은 문장이 있으면 알려줘.
3) 한 장짜리 모델 시트: 집합과 색인, 데이터와 단위, 결정변수, 필수 제약(ID·원문 인용·식·검증 방법), 목적과 우선순위, 정의, 출력 형식, 완료 기준(제안). 최적화가 아니면 요구사항 표(요구 ID, 원문 인용, 입력 → 처리 → 출력, 판정 규칙과 경계값, 검증 방법)로 바꿔 내줘.
4) 지문만으로 정해지지 않는 것. 결과를 바꾸는 닫힌 질문은 중요한 순서로 최대 5개, 질문마다 네 잠정 선택을 붙여서. 5개를 넘으면 나머지는 한 가지로 읽은 것에 넣고 결과가 바뀐다고 표시해줘. 지문에 없어 한 가지로 읽은 것은 따로.
5) 남은 시간을 조사·합의 / 첫 동작 / 확장 / 검증 / 제출 확인에 어떻게 나눌지 한 줄 제안. 따로 푸는 하위 문제가 여럿이면 몇 개인지도.
6) 쓸 수 있는 솔버와 패키지를 import로만 확인한 결과와 버전. 설치는 하지 마. 쓸 수 있는 솔버가 하나도 없으면 답의 맨 위에 한 줄로 알려줘.
지문과 데이터에 없는 입력값은 만들지 마(검사용으로 만든 입력은 검사에만 쓰면 돼). 손으로 계산해 본 값은 미검증이라고 표시해줘. 내 해석을 줄 때까지 기다려.

[2] 내 해석과 대조
내 해석은 이래: <정하는 것 / 반드시 지킬 것 / 더 좋게 할 것 / 헷갈리는 것>.
네 모델 시트와 제약 ID별로 비교해서 다른 곳만 표로 보여줘. 어느 쪽이 지문 원문에 맞는지 원문을 인용해서 말하고, 원문으로 가릴 수 없는 것은 질문 목록으로 넘겨줘.

[4] 담당자 답 반영
담당자 답: <답 원문>.
답을 필수 조건 / 기존 요구의 구체화 / 선택적 개선 / 공식 지시와의 충돌로 구분하고, 모델 시트의 어느 제약 ID가 어떻게 바뀌는지 바뀐 행만 보여줘.
구현 승인 전이면 거기서 멈추고, 이미 구현 중이면 영향받는 코드와 검사만 고쳐 다시 검증해줘.

[5] 구현 진행
구현 진행. 범위는 합의한 모델 시트 그대로야. 답을 못 받은 질문은 시트의 잠정 선택으로 두고, 답이 오면 한 곳만 고치면 되게 해줘.
계산 마감은 <HH:MM>이야. 그 뒤에는 새 해를 받지 말고 저장된 결과로 검증과 제출 확인만 해줘.
시작 전에 합의한 모델 시트와 담당자 답을 작업 기록에 옮겨 적고, VERIFICATION.md를 읽어줘. 검사는 한 명령으로 다시 돌릴 수 있게 만들어줘.
순서는 이렇게 해줘.
1) 원본 입력과 최종 출력만으로 제약 ID마다 다시 계산하는 독립 검증기를 먼저 만든다(솔버 라이브러리를 쓰지 않는다).
2) 가장 작은 실제 입력으로 입력 → 모델 → 검증 → 출력을 끝까지 잇는다. 과제가 화면을 요구하면 필수 화면에 그 결과가 뜨는 데까지가 이 단계다(꾸미기는 나중).
3) 그다음에 전체 입력으로 넓힌다. 하위 문제가 여럿이거나 풀이가 길면 전체 계산 전에 OPTIMIZATION 8절대로 소요를 어림해 먼저 알려줘.
(일정 문제일 때만) 작업 단위는 (로트, 방문 회차)로 두고, 적합한 (방문, 장비) 쌍에만 변수를 만들어줘.
시간은 배율을 곱해 정확히 정수로 만들고, 필수 제약은 벌점으로 완화하지 마. 솔버를 부를 때는 시간 한도를 넣어줘.
솔버가 없으면 PROCESS_OPTIMIZATION 1절대로 하되, 설치가 필요하면 먼저 물어봐.

[6-1] 검증만 다시 볼 때 (과제 종류와 무관하게 쓴다)
VERIFICATION.md의 고리 V1~V8을 차례로 점검해서 검증 기록표로 보여줘(고리, 검사한 것, 기대/관측과 건수, 상태). 표 위에 검사한 코드·입력의 식별자, 실행 시각, 실행한 명령과 종료 코드를 적어줘.
실행하지 않은 고리는 미실행으로 적고 이유와 다음 확인 방법을 붙여줘. 검사 건수가 0인 것은 성공으로 적지 마.
내가 직접 확인할 것(화면 조작, 원문 대조 표본)은 따로 모아 순서대로, 보여야 할 값과 함께 알려줘.

[7] 결과와 검증 보고
현재 결과를 한 번에 보고해줘. 표 위주로 짧게 쓰고 같은 내용을 두 번 쓰지 마.
- 맨 위 세 줄: 무엇이 됐는지, 무엇이 남았는지, 내가 정할 것.
- 결과: 단계별 솔버 종료 상태, 목적값, 하한, 시간 한도와 지표 값. "최적"이라는 말은 최적성이 확인됐을 때만. 하위 문제가 여럿이면 하위 문제별 상태 표.
- 검증: VERIFICATION의 검증 기록표(고리, 검사한 것, 기대/관측과 건수, 상태). 표 위에 검사한 코드·입력의 식별자, 실행 시각, 실행한 명령과 종료 코드.
- 내가 직접 확인할 것: 화면 주소, 누를 순서, 보여야 할 값, 원문 대조 표본. 내 관측을 받기 전에는 미실행으로 적어줘.
- 가정(잠정 선택 포함)과 한계.
실행하지 않은 검사는 미실행으로 적고 이유를 붙여줘. 검사 건수가 0인 것은 성공으로 적지 마.

[8] 해 없음이 나왔을 때
종료 상태가 불가능 증명(INFEASIBLE)인지 시간 안에 못 찾은 것(UNKNOWN)인지 먼저 말해줘. 시간 안에 못 찾은 것이면 [10]으로 가.
불가능 증명이면 조건을 완화해서 풀지 말고 원인부터 찾아줘.
제약 묶음(ID)을 하나씩 빼고 풀어서 어느 묶음을 빼면 풀리는지 표로 보여줘. 그 묶음의 식을 지문 원문과 나란히 놓고 부호, 경계값 포함 여부, 분모, 단위, 기준 사건, 초기 상태, 시간 범위를 대조해줘.
독해 오류가 아니라 입력 자체가 모순이면 어느 로트·어느 조건이 부딪히는지 구체적으로 적어줘.

[9] 해가 너무 쉬울 때
결과가 너무 좋아 보여(<지연 0 / 자원이 크게 남음 / 완료가 너무 빠름>). 빠뜨린 문장이 있는지 확인해줘.
방문(작업 단위)의 수가 로트별 경로 단계 수의 합과 같은지, 지문의 모든 필수 문장에 제약 ID가 붙어 있는지, 단계를 잇는 식(배정과 사용, 선택과 덮기)이 빠지지 않았는지, 현재 시각보다 앞에서 시작하는 새 작업이 없는지 세어서 보여줘.

[10] 계산 시간 관리 (풀이가 오래 걸리거나 하위 문제가 여럿일 때)
계산 마감은 <HH:MM>이고 지금은 <HH:MM>이야. 마감 뒤에는 새 해를 받지 말고 저장된 결과로 검증과 제출 확인만 해줘.
하위 문제 목록과 크기를 표로 보여주고, 가장 작은 것과 가장 큰 것을 <30>초 한도로 풀어 마감 안에 다 풀리는지 어림해줘.
모자랄 것 같으면 OPTIMIZATION 8절대로 해줘: 먼저 모든 하위 문제에 규칙으로 만든 유효한 해를 저장하고, 작은 것부터 풀되 한도는 남은 시간 ÷ 남은 개수로 그때그때 다시 잡아줘. 하나 끝날 때마다 저장하고 검증해줘.
진행 상황은 표로 보여줘: 하위 문제, 상태(최적성 확인 / 유효해만 / 규칙 해 / 아직), 목적값, 걸린 시간, 남은 시간.
필수 제약을 빼거나 대상을 줄이지 마. 시간 제한을 불가능의 증명처럼 쓰지 마.

[12] 제출 전 점검
제출 전에 확인해줘: 제출 형식과 파일 이름, 다시 실행하는 명령, 실제 제출 파일로 다시 돌린 검증 결과(VERIFICATION의 V4·V7·V8), 화면이 있으면 내가 확인한 관측 기록, 사용한 지침의 제출 여부(QUICKSTART의 제출 확인), 비밀정보 포함 여부, 미검증 항목과 한계.
구현 완료, 검증 통과, 실제 제출 완료를 구분해서 적어줘.

[13] 세션을 다시 열었을 때
playbook/AGENTS.md, PLAYBOOK.md와 앞서 쓴 조건부 문서, 작업 기록을 읽고 이어서 해줘. 구현 진행은 이미 승인했고 범위는 작업 기록의 모델 시트야. 조사와 합의를 다시 하지 말고, 마지막으로 통과한 검사부터 확인해줘.
